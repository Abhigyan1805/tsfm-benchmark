# REPORT — tsfm-benchmark

Full write-up of the benchmark: setup, results, negative results, and
limitations. `README.md` carries the headline; `PLAN.md` is the plan of record.

This report currently covers the **first real end-to-end run**: the five local
CPU families on the real Monash *Electricity Hourly* dataset. The deep and TSFM
zero-shot tiers are **not** part of this run (GPU work is a separate slice); the
pending list below is explicit.

## 1. Setup

| Item | Value |
| --- | --- |
| Dataset | Monash *Electricity Hourly* (Zenodo record 4656140), CC-BY-4.0, 321 hourly series |
| Evaluation subset | 24 evenly-spaced series (T1…T308) frozen in the committed split manifest |
| Split | 60/20/20 train/val/test, `context_length=168`, rolling origins scored on the test period |
| Horizons | 24 / 48 / 96 / 192 steps (the primary sweep) |
| Metrics | MAE, RMSE, seasonal MASE (season 24), sMAPE; latency p50/p95; fit wall-clock |
| Bounded subset | **All 24 frozen series, but origins sampled every 240 steps (10 days)**, giving 21–22 origins per series per horizon instead of the manifest's 24-step stride. The frozen boundaries, leakage guarantees, and metric definitions are unchanged. The full-stride sweep is a follow-up. |
| Classical engine | `statsforecast` 2.0.1 for both `auto_ets` and `auto_arima` (the model tier's preferred engine; the `statsmodels` AIC-grid fallback was not used). The frozen `RESULT_COLUMNS` schema has no engine column, so the engine is recorded here and pinned by the installed revision. |
| Memory tracking | Disabled for this bounded run (`track_memory: false`): `tracemalloc` peak tracking makes statsforecast's `auto_arima` ~3.5× slower (measured 41s vs 12s for one 22-origin series). `peak_mem_mb` is therefore empty and memory telemetry is a follow-up; latency and fit wall-clock are measured. |

`auto_arima` runs statsforecast's default **non-seasonal** search. A seasonal
(m=24) search is orders of magnitude slower per window and pushes a single run
past a day of CPU; the daily seasonal structure is carried instead by
`seasonal_naive`, `auto_ets` (season 24), and the XGBoost lag features
`[1, 2, 3, 24, 25, 48]`.

### Reading the results

- **The seasonal floor is hard to beat.** `seasonal_naive` (repeat the last
  daily cycle) is the best model at every horizon (MASE 1.00–1.30). Hourly
  electricity demand is strongly daily-periodic, so a seasonal reference is a
  serious baseline, not a formality. Any model that cannot represent the daily
  cycle starts behind.
- **Classical ETS is the strongest learned model.** `auto_ets` with season 24
  tracks `seasonal_naive` closely (MASE 1.14 at h=24 rising to 1.55 at h=192)
  while remaining two to three orders of magnitude more expensive per forecast
  (≈177 ms vs ≈0.1 ms p50). The accuracy gain over the seasonal floor is small;
  the cost is not.
- **XGBoost lags are competitive but not better.** `xgboost_lags` sits between
  `auto_ets` and the floors (MASE 1.29–1.94) at roughly half the latency of ETS.
  The calendar features are positional in the rolling backtest (the protocol
  passes numpy windows, so `_CalendarIndex` cannot see a datetime index); the
  lag features, including lag 24, carry the seasonality.
- **Non-seasonal ARIMA is the cautionary result.** `auto_arima` (MASE 3.03–3.93)
  beats the `naive` floor but is far behind every seasonal model, and it is the
  most expensive model at ≈512–530 ms p50. A non-seasonal ARIMA is the wrong
  tool for daily-periodic hourly demand; the honest comparison is the seasonal
  ARIMA that the compute budget deferred.
- **Accuracy degrades gracefully with horizon** for every family; the ordering
  is stable across 24/48/96/192.

## 4. Reproduce

```sh
pip install -e ".[dev,models,report]"
python -m tsbench.data.build_catalog --materialize   # network + checksum verify
make backtest                                        # 24h primary, 5 families
make horizons                                        # 48/96/192 on the same frozen boundaries
make report                                          # summary CSV + figures from results/
```

`make backtest` and `make horizons` write run directories under `results/`
(gitignored). `make report` reads them, keeps the newest run per `config_hash`,
and writes the committed `docs/results_summary.csv` and `docs/figures/`.

## 5. Limitations

- The bounded 240-step origin stride yields 21–22 origins per series per
  horizon, not the manifest's full 24-step resolution. Every number here is a
  real measurement on the frozen boundaries, but the confidence intervals of the
  means are wider than the full sweep's.
- `peak_mem_mb` is not measured in this run; the cost axis here is latency only.
- `auto_arima` is non-seasonal and the XGBoost calendar features are positional,
  as noted above. Both are documented, reproducible choices, not silent ones.
- No TSFM appears here yet, so the headline research question ("when do TSFMs
  beat conventional models?") is not answered by this run; it establishes the
  conventional baselines the TSFMs will be measured against.
