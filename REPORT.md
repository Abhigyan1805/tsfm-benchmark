# REPORT — tsfm-benchmark

Full write-up of the benchmark: setup, results, negative results, and
limitations. `README.md` carries the headline; `PLAN.md` is the plan of record.

This report covers the **complete end-to-end run**: all five local CPU families
(naive, seasonal-naive, ETS/ARIMA, XGBoost) **and** the GPU tier (seeded LSTM
and small Transformer, plus zero-shot TimesFM 2.5 and Chronos-Bolt) on the real
Monash *Electricity Hourly* dataset. Both tiers are measured on the **same
frozen windows** — the run metadata records the identical split-manifest digest
`970cc0b4…6d768` for the CPU and GPU runs. The measured/pending split is in
§3.

## 1. Setup

| Item | Value |
| --- | --- |
| Dataset | Monash *Electricity Hourly* (Zenodo record 4656140), CC-BY-4.0, 321 hourly series |
| Evaluation subset | 24 evenly-spaced series (T1…T308) frozen in the committed split manifest |
| Split | 60/20/20 train/val/test, `context_length=168`, rolling origins scored on the test period |
| Horizons | 24 / 48 / 96 / 192 steps (the primary sweep) |
| Metrics | MAE, RMSE, seasonal MASE (season 24), sMAPE; latency p50/p95; fit/train wall-clock |
| Bounded subset | **All 24 frozen series, but origins sampled every 240 steps (10 days)**, giving 21–22 origins per series per horizon instead of the manifest's 24-step stride. The frozen boundaries, leakage guarantees, and metric definitions are unchanged. The full-stride sweep is a follow-up. |
| Classical engine | `statsforecast` 2.0.1 for both `auto_ets` and `auto_arima` (the model tier's preferred engine; the `statsmodels` AIC-grid fallback was not used). The frozen `RESULT_COLUMNS` schema has no engine column, so the engine is recorded here and pinned by the installed revision. |
| Deep tier | Seeded `LSTMForecaster` / `TransformerForecaster`, GPU-trained from scratch at each origin with a fixed budget: context 32, hidden 32, 50 epochs, lr 1e-2, batch 64 (Transformer: 2 layers, 4 heads, feed-forward 64). Seed 20240919. |
| TSFM tier | Zero-shot `TimesFM25` (`google/timesfm-2.5-200m-pytorch`, Apache-2.0, revision `1d952420…`, 231M params) and `ChronosBolt` (`amazon/chronos-bolt-base`, Apache-2.0, revision `5d9f166d…`, 205M params). No weights are downloaded unless `TSBENCH_ALLOW_MODEL_DOWNLOAD=1`; no non-permissive checkpoint is reachable. `warmup: true` primes the checkpoint load and TimesFM compile before the first scored window. |
| Memory tracking | `peak_mem_mb` is a **GPU-tier-only** column. The CPU configs run `track_memory: false` because `tracemalloc` makes statsforecast's `auto_arima` ~3.5× slower (measured 41s vs 12s for one 22-origin series), so their cells are empty. On the GPU tier it is the CUDA allocator's per-window peak above the resident checkpoint (a process-level cache keeps the weights loaded across origins), so it is comparable within the GPU tier and is **not** total model memory. |

`auto_arima` runs statsforecast's default **non-seasonal** search. A seasonal
(m=24) search is orders of magnitude slower per window and pushes a single run
past a day of CPU; the daily seasonal structure is carried instead by
`seasonal_naive`, `auto_ets` (season 24), and the XGBoost lag features
`[1, 2, 3, 24, 25, 48]`.

The reported **seasonal MASE** uses the rolling `context_length` (168-value)
lookback as its scale base — `backtest.py` passes `y_train=context_values` — not
the full in-sample training slice, so it is a rolling-context variant of the
textbook statistic; the reference series is the only thing that differs. The
independent audit measured a **+8.77%** shift in the m=24 denominator on a
synthetic 26,304-point series. The drift is largely model-independent, so it
moves levels more than rankings. See `tsbench.evaluation.metrics.mase`.

Run provenance: CPU telemetry under `docs/telemetry/cpu/`, GPU telemetry under
`docs/telemetry/gpu/`; each run's `run.json` carries the git sha
(`7fd54a3…` CPU, `dcb2c10…` GPU), config hash, split-manifest digest, and
`measured: true`.

### Reading the results

- **The zero-shot TSFMs win outright.** `chronos_bolt` is the best model at
  every horizon (MASE 0.79 / 0.85 / 0.95 / 1.04 for h=24/48/96/192), ahead of
  `timesfm25` (0.88 / 0.96 / 1.04 / 1.11) and comfortably ahead of the seasonal
  floor (`seasonal_naive` 1.00 / 1.11 / 1.25 / 1.30). Both foundation models
  beat every trained model **zero-shot**, with no fitting on the target series.
- **Chronos-Bolt also leads on cost.** Its median forecast is 35 ms at h=24 and
  34 ms at h=48, rising to 75/114 ms at h=96/192 (its decoder is chunked beyond
  64 steps); TimesFM 2.5 is slower (116–214 ms). Both are cheaper than the
  trained deep models and competitive with classical ETS, so they sit on the
  accuracy/cost frontier, not behind it.
- **The seasonal floor is hard to beat for trained-from-scratch models.**
  `seasonal_naive` (repeat the last daily cycle) stays at MASE 1.00–1.30, so a
  conventional model must represent the daily cycle to compete. `auto_ets`
  (season 24) tracks it at 1.14–1.55 but is ~1700× more expensive per forecast
  (≈177 ms vs ≈0.1 ms p50).
- **XGBoost lags are competitive but not better.** `xgboost_lags` sits between
  `auto_ets` and the floors (MASE 1.29–1.94) at roughly half the latency of ETS.
  The calendar features are positional in the rolling backtest (the protocol
  passes numpy windows, so `_CalendarIndex` cannot see a datetime index); the
  lag features, including lag 24, carry the seasonality.
- **The trained deep tier is the negative result.** At the fixed 50-epoch
  budget the seeded LSTM (1.75→3.62) and Transformer (1.74→2.04) are the weakest
  learned models, behind classical ETS, XGBoost, and the seasonal floor, while
  being the *most* expensive: ≈342 ms (LSTM) and ≈585 ms (Transformer) p50, with
  a median 0.32 s / 0.58 s of GPU training per scored window. A small
  from-scratch recurrent/attention model is not competitive here; the zero-shot
  pretrained models dominate it on every axis.
- **Non-seasonal ARIMA is the cautionary result.** `auto_arima` (MASE 3.03–3.93)
  beats the `naive` floor but is far behind every seasonal model, and it is the
  most expensive classical model at ≈512–530 ms p50.
- **Accuracy degrades gracefully with horizon** for every family; the ordering
  is stable across 24/48/96/192 (the one swap: at h=24 the LSTM is marginally
  better than the Transformer, at every longer horizon the Transformer is
  better).

## 4. Reproduce

```sh
pip install -e ".[dev,models,report]"
python -m tsbench.data.build_catalog --materialize   # network + checksum verify
make backtest                                        # 24h primary, 5 CPU families
make horizons                                        # 48/96/192 on the same frozen boundaries
make report                                          # summary CSV + figures from results/ + telemetry
```

The GPU tier runs through the Kaggle batch handoff (`docs/colab-handoff.md`):

```sh
python scripts/kaggle_run.py experiments \
    --config configs/experiments/gpu.yaml \
    --config configs/experiments/gpu_h48.yaml \
    --config configs/experiments/gpu_h96.yaml \
    --config configs/experiments/gpu_h192.yaml \
    --out results --ref "$(git rev-parse HEAD)" \
    --pip 'timesfm[torch]' --pip chronos-forecasting --timeout 14400
```

The kernel asserts the cloned ref carries the process-level TSFM backend cache
(without it the checkpoint reloads and TimesFM recompiles for every one of
~2000 origins), refreshes its results bundle after each config so a runtime
limit cannot discard completed configs, and resolves the dataset mount whether
Kaggle exposes it at `/kaggle/input/<slug>` or `/kaggle/input/datasets/<owner>/<slug>`.

`make backtest`, `make horizons`, and the GPU route write run directories under
`results/` (gitignored); the per-run raw telemetry is copied to
`docs/telemetry/{cpu,gpu}/<run_id>/` as committed evidence, and `make report`
reads both. CPU rows: `7fd54a3…`; GPU rows: `dcb2c10…`.

## 5. Limitations

- The bounded 240-step origin stride yields 21–22 origins per series per
  horizon, not the manifest's full 24-step resolution. Every number here is a
  real measurement on the frozen boundaries, but the confidence intervals of the
  means are wider than the full sweep's.
- `peak_mem_mb` is GPU-tier-only: it is the CUDA allocator's peak above the
  resident (cached) checkpoint, so it is not total model memory and the CPU
  cells are empty. The cross-tier cost axis in the figure is latency only.
- The deep tier is a small fixed-budget model trained from scratch per origin,
  not a tuned architecture; its poor showing is a result about that budget, not
  about deep forecasting in general. The TSFMs, by contrast, are pretrained on
  large corpora that plausibly overlap electricity-demand structure, which is
  the intended advantage of the foundation-model line and not a like-for-like
  architecture comparison.
- `auto_arima` is non-seasonal and the XGBoost calendar features are positional,
  as noted above. Both are documented, reproducible choices, not silent ones.
- Chronos-Bolt emits an upstream warning for prediction lengths > 64; the
  h=96/192 forecasts decode in chunks and the warning is recorded in the kernel
  log. This is a model-card caveat, not a measurement failure.
- The two tiers ran on different hardware (CPU host vs Kaggle T4 GPU), so
  `train_seconds` and `peak_mem_mb` are only comparable **within** a tier; the
  cross-tier comparison is accuracy and per-forecast latency.
